## §2 ビジネス要件

### 2.1 背景・課題
日常使いしている Excel プロジェクト `12months-calendar.xlsx`（12ヶ月を1画面で俯瞰）を出発点とする。Excel は色・レイアウトにこだわれる一方、①動作・操作の体感速度、②ズームや時間計算などのインタラクション、③配布・マルチデバイス性に制限がある。この制約を解き、"格"を上げるために Web アプリ（将来 iOS アプリ）化する。

### 2.2 ビジョン
「**とにかく速いカレンダーアプリ**」。12ヶ月を一望する俯瞰性と体感速度を核に、予定を管理しない人でも毎日開きたくなる日常ツールを目指す。

### 2.3 ターゲットユーザー
- **一次ユーザー（MVP基準）**: 開発者本人（Excelを日常使いしている当事者＝ドッグフーディング）
- **拡張後**: 四半期・月末・納期を意識するビジネス層／速度・効率重視のガジェット層／六曜・和風月名など暦文脈を好む層

| ID | ペルソナ | ニーズ |
|----|---------|-------|
| STK-01 | 開発者本人（PO兼一次ユーザー） | Excelを卒業できる高速な12ヶ月俯瞰・時間計算 |
| STK-02 | ビジネス層（拡張） | 「あと何日」を即把握、俯瞰での計画 |
| STK-03 | 効率・速度重視層（拡張） | 軽いUI・キーボード操作・時間計算 |

### 2.4 提供価値・UVP
**主軸 = 体感速度。** 「少人数だからこそ実現できる極端なパフォーマンス最適化と、大手が実装しない小回りの効く機能」で差別化する。掛け算の要素:
- BR-01 12ヶ月の俯瞰性（Excelプロジェクトの核を継承）
- BR-02 体感速度（起動・遷移・操作すべて）← **一番の武器**
- BR-03 日本の暦文脈（六曜・和風月名・遊びセクション・祝日）
- BR-04 時間計算（電卓）という"隠れ最強"機能

### 2.5 競合・立ち位置
| 競合 | 特徴 | tonihaya の立ち位置 |
|------|------|-------------------|
| benri.com/calendar | 多機能な暦照会・遠い年まで遡及 | 速度・UI/UX・時間計算で**上位互換**を狙う |
| Google/Apple カレンダー | 予定管理に最適化 | **共存・補完**。「見る・数える・計算する」高速ビューアーとして差別化 |

**勝ち筋**: 少数ユーザー前提だからこそ許容できる極端な速度最適化と、機動的な機能実装。

### 2.6 ビジネスモデル・収益化
段階的に開放する（MVPはマネタイズなし）:
1. **広告**（無料層で母数を確保）
2. **サブスク**（過去・現在・未来の予定管理）
3. **AIクレジット**（フルプラン: 自然言語時間計算など）
- 将来: 第三者共有・チーム共有、外部カレンダー/アプリ連携、MCP連携、ウィジェット

### 2.7 成功基準（MVP）
- **主要**: ポートフォリオとしての完成（技術力・UI/UX・速度を示す作品として公開できる品質）
- **副次**: 開発者本人が既存Excelを卒業し毎日開くレベル（ドッグフーディング成立）

### 2.8 スコープ（MVP / 将来）
**MVP必須（Must）**
- BR-S01 起動スプラッシュ（〜1秒）→ 即デフォルト12月俯瞰表示
- BR-S02 12ヶ月俯瞰 + 本日日付の強調（太字・+α情報）
- BR-S03 暦レイアウト（六曜・土休色分け・和風月名・英語月名・太線/細線）
- BR-S04 ズーム遷移（月→日→時刻→分、ピンチ/クリック、逆ズームアウト、トランジション）
- BR-S05 年移動（1年/10年/任意入力）・遠い年（〜645年）遡及
- BR-S06 遊びセクション（土曜/月末/四半期末/年末まで○日）
- BR-S07 祝日一覧・ジャンプ
- BR-S08 時間計算（電卓）**基礎版**（○時○分＋○時○分／差分計算などルールベース）

**将来（Could / Post-MVP）**
- 予定管理（保存）、広告、サブスク、AIクレジット、AI自然言語解釈、共有/チーム、外部連携、MCP、ウィジェット

### 2.9 前提・制約
- 開発体制は本人単独。1ヶ月でのMVPリリースを志向。
- 本格プロダクト前提の設計（非機能・セキュリティ・課金・スケールを最初から織り込む）だが、実装は段階リリースする。

## §3 業務要件

### 3.1 利用デバイス・環境
- **MVP最適化対象**: PC（広い画面で12ヶ月俯瞰が最も生きる）
- **拡張**: レスポンシブ対応でスマホ／タブレット。将来 iOS ネイティブ・ウィジェット。
- ブラウザ: モダンブラウザ（Chrome/Safari/Edge/Firefox 最新）

### 3.2 主要利用シナリオ（優先度順）
| 優先 | シナリオ | 説明 |
|------|---------|------|
| 1 | 俯瞰して計画 | 12ヶ月を見渡し先の予定・節目を把握、ズームで深入りして検討 |
| 2 | 今日の確認＋あと何日 | 本日と、土曜/月末/四半期末/年末までの日数を即把握 |
| 3 | 時間計算ツール | カレンダーとは独立に時間計算（電卓）を高速利用 |

### 3.3 データライフサイクル
- **MVP: 完全ステートレス**（サーバDB・ログインなし）。カレンダー・暦注・遊びセクション・時間計算はすべてクライアント計算で完結し、極限の体感速度を実現する。
- ごく少数のUI設定（テーマ・表示オプション）はローカル（localStorage）に保持しうる。
- **制約（重要）**: 将来ログイン・予定保存（DB永続化）を**後付けで追加できる**アーキテクチャとする。MVPのステートレス実装が将来の永続化の障害にならないよう境界を設計する。<!-- 要レビュー: 永続化拡張点を§4で明示 -->

### 3.4 権限・ロール
- **MVP**: 認証なし。全機能を匿名で利用可能。
- **将来**: ログインユーザー（予定保存・サブスク）、チーム/共有ロール、管理者。

### 3.5 利用頻度
- 毎日（日常ツールとして開くことを想定）。ゆえに起動〜初期表示の速度が最重要。

## §4 システム要件・アーキテクチャ

### 4.1 アーキテクチャ方針
**MVPはクライアントオンリーの静的SPA/SSG**。カレンダーグリッド生成・祝日/六曜/旧暦・遊びセクション・時間計算をすべてブラウザ内で計算し、CDN静的配信で極限の体感速度を実現する。ドメイン計算層 / UI層 / 状態層を分離し、将来の永続化・API化に備えた「データポート」の継ぎ目を設ける。

### 4.2 アーキテクチャ概要（C4: Context）
- MVP: ユーザー ⇄ ブラウザ（Next.js 静的アプリ、全計算をローカル実行）⇄ CDN（静的アセット配信）
- 将来: ＋ Go バックエンド API（予定保存・サブスク・AIプロキシ・暦/祝日API）＋ DB（PostgreSQL 等）＋ 認証

### 4.3 技術スタック（確定）
| 層 | 採用 | 備考 |
|----|------|------|
| フロント言語 | TypeScript | strict |
| フレームワーク | Next.js 15（App Router）+ React 19 | MVPは `output: 'export'`（静的） |
| スタイリング | Tailwind CSS | my-web と統一 |
| アニメ/遷移 | View Transitions API + Framer Motion（motion） | ズーム遷移（月→日→時刻→分） |
| 状態管理 | React state + URL状態、UI設定は localStorage | MVPはサーバ状態なし |
| 日付/暦計算 | 自作TSモジュール（+ 軽量lib、Moment不使用） | 祝日・六曜・旧暦・遊びセクション |
| テスト | Vitest（+ 将来 Playwright E2E） | my-web と統一 |
| ホスティング | Vercel（MVP）／将来 Cloudflare 検討 | feature→develop→main 自動デプロイ |
| 将来バックエンド | **Go**（v1.1 以降） | 予定/サブスク/AI/暦API |

### 4.4 暦・計算ロジック方針
- **グレゴリオ暦グリッド**: 任意年月の曜日配置を算出（〜645年など広範囲、うるう年・改暦は割り切りを明記）。<!-- 要レビュー: 1873年グレゴリオ改暦前の扱い（表示は先発グレゴリオ暦で近似）-->
- **日本の祝日**: 固定祝日＋ハッピーマンデー＋春分/秋分（天文計算近似）＋振替休日・国民の休日をアルゴリズムで生成。
- **六曜**: 旧暦（太陰太陽暦）変換から算出。
- **和風月名**: 睦月〜師走のマッピング。
- **遊びセクション**: 本日基準で土曜/月末/四半期末/年末までの残日数を算出。
- **時間計算（電卓）基礎版**: 時刻±時間、時刻差分などルールベース演算。将来AI自然言語解釈を追加。

### 4.5 パフォーマンス設計指針（§6で数値化）
- 静的配信＋最小クライアントJS、コード分割、遅延読込。
- ズーム遷移は GPU 合成（transform/opacity）中心で 60fps 維持。
- 計算はメモ化・Web Worker 退避も検討（重い暦計算時）。

### 4.6 拡張点（将来の後付け設計）
- **永続化ポート**: 予定・設定の read/write を抽象インターフェース化し、MVPは localStorage 実装、将来 Go API 実装に差し替え可能とする。
- **認証シーム**: 匿名前提だが、ユーザーコンテキストを注入できる構造にしておく。
- **課金/AIフラグ**: フィーチャーフラグで段階開放（広告→サブスク→AIクレジット）。

### 4.7 データモデル（MVP）
- サーバ側データモデルなし。クライアント内の一時状態（表示年月・ズームレベル・設定）のみ。将来のスキーマ（User / Event / Subscription 等）は仕様書フェーズで設計。

### 5.2 ズームレベル定義（MVP）

| レベル | 表示 | 操作 |
|--------|------|------|
| L0 俯瞰 | 12ヶ月グリッド | 既定表示。月をクリック/ピンチアウトでL1へ |
| L1 単月 | 拡大した1ヶ月 | 日をクリックでL2へ／戻るでL0 |
| L2 単日 | 1日の詳細（曜日・六曜・祝日・+α） | 時刻表示へ／戻るでL1 |
| L3 時刻 | その日の時刻軸（時間帯ビュー） | MVPの最深部。分レベルは将来 |

### 5.3 時間計算（電卓）基礎版・演算セット（FR-10 詳細）

- **時刻 ± 時間**: 例 14:30 + 0:45 = 15:15（日跨ぎの繰上/繰下対応）
- **時刻間の差分**: 例 09:00 〜 17:30 = 8時間30分
- **日付 ± 日数 / 日付間の差分**: 例 7/4 +30日、7/4〜12/31 = ○日（カレンダー連携）
- **時間の加減算**: 例 1:20 + 2:50 = 4:10（時刻でなく純粋な時間量）
- 将来: AI自然言語解釈（「○時の○時間○分後は？」等）→ FR-F02

## §7 デザイン・UI/UX要件

### 7.1 デザイン原則
- **モノクロ基調 × 意味のある最小アクセント**。忙しく時間のないユーザーが主対象のため、視覚ノイズを最小化し、色は「意味」にのみ使う。
- Excelの多色配色はそのまま移植せず、**情報の意味（日曜/祝日・本日・土曜）だけを色で残す**。
- ミニマル/フラットを基調。高密度な12ヶ月グリッドの可読性を最優先。

### 7.2 カラーシステム（方向性）
| 役割 | 方針 |
|------|------|
| 基調 | グレースケール（背景・罫線・平日文字） |
| 日曜・祝日 | 赤系アクセント1色（Excel `#C00000` を彩度調整） |
| 本日 | 強調アクセント（1色。太字大きめ数字と併用） |
| 土曜 | 控えめな寒色/グレー寄りアクセント |
| 罫線 | 太線＝月/週区切り、細線＝日区切り（グレー階調） |

<!-- 要レビュー: 正確なパレット値・コントラスト比(AA)は仕様書§6 screen-spec で確定 -->

### 7.3 タイポグラフィ
- サンセリフ。数字は等幅数字（tabular numerals）で桁揃え。
- **本日**は太字・大きめ数字で最も目立たせる（+α情報を近接配置）。
- 月ラベルは「1月 / January / 睦月」を階層表示。

### 7.4 レイアウト
- 12ヶ月俯瞰: グリッド配置（3×4 等）。1画面完結を基本。
- 遊びセクション・時間計算（電卓）・祝日一覧は **Bentoカード** でモジュール的に配置。
- ズームレベルごとにレイアウトを再構成（俯瞰→単月→単日→時刻）。

### 7.5 テーマ
- ライト（既定）／ダーク／システム追従の3モードを切替可能。設定は localStorage 保持。
- ライトはExcelの白背景の系譜、ダークは省電力・夜間可読を意識。

### 7.6 モーション
- ズーム遷移はトランジション付き（View Transitions / transform・opacity中心）で60fps。
- 過度なアニメは避け、速度感を損なわない範囲に留める。
- `prefers-reduced-motion` を尊重。

### 7.7 参考
- 情報密度・遠い年遡及は benri.com/calendar を参照しつつ、速度・UI/UXで上位互換を狙う。

## §12 セキュリティ要件

### 12.1 準拠レベル
- MVP: **OWASP ASVS 5.0 Level 1**。認証・決済追加時に **Level 2** へ引き上げ。

### 12.2 MVPのセキュリティ要件（SEC）

| ID | 要件 |
|----|------|
| SEC-01 | 全通信 HTTPS、HSTS 有効 |
| SEC-02 | Content-Security-Policy を設定（インラインスクリプト最小化） |
| SEC-03 | セキュアヘッダ（X-Content-Type-Options / Referrer-Policy / Permissions-Policy） |
| SEC-04 | 入力検証: 年入力（範囲・数値）、電卓入力（時刻/時間フォーマット）をバリデーション・サニタイズ |
| SEC-05 | XSS対策: React自動エスケープ、`dangerouslySetInnerHTML` 不使用 |
| SEC-06 | シークレットをクライアントにハードコードしない（秘密は将来のサーバ側のみ） |
| SEC-07 | 依存性の自動監視（Dependabot + CI で `npm audit`）、既知脆弱性の除去 |
| SEC-08 | localStorage には機微情報を置かない（表示設定のみ） |
| SEC-09 | プライバシー: 計測はCookieレス・個人情報の収集最小化 |

### 12.3 将来（認証・決済追加時）
- 認証: **NIST SP 800-63B-4** 準拠、パスワードは **Argon2id**、レート制限・MFA検討。
- 決済: **PCI DSS v4.0.1 SAQ-A**（Stripeでカード情報非保持）。
- ASVS **Level 2** へ引上げ、CSRF対策・セッション管理を実装。

## §13 テスト・品質保証要件

### 13.1 テスト戦略
- **TDD**（RED→GREEN→REFACTOR）を基本とする。
- **単体（Vitest）**: 暦計算（グレゴリオグリッド・祝日・六曜・旧暦）・遊びセクション日数・時間計算（電卓4演算）を厚くカバー。境界値（うるう年・年跨ぎ・645年・日跨ぎ）を重点。
- **核心E2E（Playwright）**: 起動→俯瞰表示、ズーム遷移、年移動、電卓の主要フローを担保。

### 13.2 品質目標
