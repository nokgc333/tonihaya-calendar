## §2 概要とアーキテクチャ

### 2.1 システム構成（C4: Container）
- **MVP**: Browser（Next.js静的アプリ：UI層／状態層／ドメイン計算層）⇄ CDN（Vercel、静的アセット）。サーバ処理なし。
- **将来**: ＋ Go API（予定/サブスク/AI/暦）＋ PostgreSQL ＋ 認証。

### 2.2 レイヤリング
```
UI層（React components / screens）
  ↓ 参照
状態層（表示年月・ズームレベル・設定：React state + URL + localStorage）
  ↓ 参照
ドメイン計算層（pure TS：暦グリッド・祝日・六曜・旧暦・遊びセクション・時間計算）
  ↕ 抽象ポート
永続化ポート（MVP: localStorage 実装 / 将来: Go API 実装）
```
- ドメイン計算層は**副作用なしの純粋関数**で構成し、単体テストを厚くする。
- 永続化・課金・認証・AIは**ポート（インターフェース）**で抽象化し、後付け実装を差し替え可能にする。

### 2.3 データフロー（例：ズーム）
ユーザー操作 → 状態層がズームレベル/対象日を更新 → URL反映（共有可能）→ UI層がView Transitionで再描画（ドメイン計算層から必要データを取得）。

## §4 データ設計

### 4.1 MVP: サーバデータなし
MVPはステートレス。永続化するのはUI設定のみ（localStorage）。

### 4.2 localStorage スキーマ（`tonihaya.settings.v1`）
```jsonc
{
  "version": 1,
  "theme": "light" | "dark" | "system",   // 既定 "system"
  "weekStart": "sun" | "mon",              // 既定 "sun"
  "showRokuyo": true,                       // 六曜表示
  "showWafuMonth": true,                    // 和風月名表示
  "lastViewedYear": 2026                     // 任意
}
```
- キーは名前空間 + バージョン付き（`tonihaya.settings.v1`）でマイグレーション可能に。
- 機微情報は保存しない（SEC-08）。

### 4.3 将来スキーマ（参考・Post-MVP）
- `User`（id, email, plan, createdAt）
- `Event`（id, userId, date, time?, title, memo, visibility）
- `Subscription`（id, userId, plan, status, provider: stripe|appstore|googleplay）
- PII分類: email=PII（保持期間・削除フローは決済/認証実装時に定義）。<!-- 要レビュー -->

## §8 ビジネスロジック・計算式

> 対応年 **1950–2150**（全要素正確・両端10年単位）。645年等は参考範囲（MVP非対応、将来グリッドのみ参考表示を検討）。

### 8.1 グレゴリオ暦グリッド（`domain/calendar`）
- 入力: 年・月。出力: 週配列（週開始曜日設定に従う）、各日に {日, 曜日, 祝日?, 六曜?, 和風月名(月単位)}。
- 1950–2150 は先発グレゴリオ暦で連続。うるう年判定は標準規則。

### 8.2 日本の祝日（`domain/holiday`）
- **固定祝日**: 元日(1/1)、建国記念の日(2/11)、天皇誕生日(2/23, 2020〜)、昭和の日(4/29)、憲法記念日(5/3)、みどりの日(5/4)、こどもの日(5/5)、山の日(8/11)、文化の日(11/3)、勤労感謝の日(11/23)。
- **ハッピーマンデー**: 成人の日(1月第2月, 2000〜)、海の日(7月第3月)、敬老の日(9月第3月)、スポーツの日(10月第2月)。
- **天文計算**: 春分の日(3/19〜21)・秋分の日(9/22〜24)を近似式で算出（1950–2150で有効）。
- **振替休日**（祝日が日曜→翌平日）・**国民の休日**（祝日に挟まれた平日）を導出。
- **歴史的変更を反映**: 成人の日(1/15→第2月, 2000)、天皇誕生日の変遷、法改正・特例（五輪移動等）を**年代別ルール**で正確化。
- 実装方針: 年代考慮のルールエンジンを自作し、既知データ（内閣府公表）でテスト。<!-- 要レビュー: ライブラリ採用可否は実装時に評価 -->

### 8.3 六曜（`domain/rokuyo`）
- 旧暦（太陰太陽暦）の月・日から算出: `六曜index = (旧暦月 + 旧暦日) mod 6`（先勝=0…赤口=5、正しいラベル対応を定数化）。
- 旧暦変換（`domain/lunar`）が前提。1873年改暦以降で有効（1950–2150は全域可）。

### 8.4 旧暦変換（`domain/lunar`）
- 新月（朔）と二十四節気（中気）から月建・閏月を決定する定気法ベース。
- 実装方針: 朔・中気の天文計算 or 事前計算テーブル（1950–2150）を採用。精度・サイズ・速度を仕様書実装時に比較。<!-- 要レビュー: 天文計算 vs テーブル -->

### 8.5 遊びセクション（`domain/countdown`）
- 本日基準で「次の土曜まで／月末まで／四半期末(3,6,9,12月末)まで／年末まで」の残日数を算出（当日=0または「本日」表示ルールを定義）。

### 8.6 時間計算（電卓）（`domain/timecalc`）
- 内部表現は分（整数）に正規化。
- **①時刻±時間**: `(時刻分 ± 時間分) mod 1440`、日跨ぎ回数を併記。
- **②時刻間の差分**: `(終了 − 開始 + 1440) mod 1440` を時間:分へ。
- **③日付±日数／日付間の差分**: 通日（epoch日）で加減算・差分。
- **④時間の加減算**: 純粋な分量の加減算（時刻でない、上限なし）。
- 入力: 電卓風ボタン＋テキスト（`14:30+45` 形式パーサ）。バリデーション（SEC-04）。
- 将来: AI自然言語解釈（FR-F02）を同ポート経由で追加。

## §9 セキュリティ実装

### 9.1 通信・ヘッダ
- 全通信HTTPS、**HSTS**（`max-age=63072000; includeSubDomains; preload`）。
- **CSP**（例・静的サイト向け）:
  ```
  default-src 'self';
  script-src 'self';
  style-src 'self' 'unsafe-inline';   /* Tailwind運用に応じ最小化 */
  img-src 'self' data:;
  connect-src 'self' https://*.sentry.io <analytics>;
  frame-ancestors 'none'; base-uri 'self'; object-src 'none';
  ```
- 追加ヘッダ: `X-Content-Type-Options: nosniff` / `Referrer-Policy: strict-origin-when-cross-origin` / `Permissions-Policy`（不要APIを無効）。
- 配信先（Vercel）の `vercel.json` / `next.config` で設定。

### 9.2 入力検証（SEC-04）
- 年入力: 整数・範囲 1950–2150、範囲外はクランプ＋通知。
- 電卓入力: 時刻 `HH:MM`（0–23:0–59）、時間量・日数は非負整数、パーサで厳格検証しエラーメッセージ提示。
- 全出力はReactの自動エスケープ（`dangerouslySetInnerHTML` 不使用、SEC-05）。

### 9.3 シークレット・依存
- クライアントに秘密を置かない（SEC-06）。公開可能値のみ `NEXT_PUBLIC_*`。
- **Dependabot** 有効化＋CIで `npm audit`（SEC-07）。

### 9.4 将来（認証・決済）
- パスワード: **Argon2id**（メモリ64MB/反復3/並列4目安）、NIST SP 800-63B-4準拠。
- TLS1.2+/1.3、決済は Stripe（PCI DSS SAQ-A、カード情報非保持）。
- CSRFトークン・セッション管理・レート制限を実装（ASVS L2）。

## §11 インフラとRunbook

### 11.1 デプロイ構成
- Vercel（静的）。`feature → develop → main`、main マージで本番自動デプロイ、PRごとにプレビュー。
- ブランチ保護: main直push禁止、CI緑を必須。

### 11.2 CI パイプライン（GitHub Actions・概略）
```yaml
on: { push: { branches: [develop, feature] }, pull_request: { branches: [main, develop] } }
jobs:
  verify:
    steps:
      - checkout / setup-node(22) / npm ci
      - npm run lint
      - npm run type-check
      - npm run test          # vitest（カバレッジ）
      - npm run build         # 静的ビルド
      - lighthouse-ci         # パフォーマンスSLO検証
```

### 11.3 環境変数インベントリ（MVP）
| 変数 | 必須 | 既定 | 説明 |
|------|------|------|------|
| `NEXT_PUBLIC_SENTRY_DSN` | 任意 | — | Sentry（フロント） |
| `NEXT_PUBLIC_ANALYTICS_ID` | 任意 | — | 軽量アナリティクス |
- MVPは秘密不要（クライアント公開値のみ）。将来の決済/AI/DBはサーバ側で追加。

### 11.4 Runbook（主要シナリオ）
1. **デプロイ失敗**: CIログ確認 → 直前緑コミットへ Vercel でロールバック → 原因修正して再デプロイ。
2. **パフォーマンス劣化（SLO割れ）**: Lighthouse-CI/Web Vitalsで特定 → バンドル増分・再レンダを調査 → コード分割/メモ化で是正。
3. **依存脆弱性**: Dependabot PR → 影響評価 → 更新・テスト → マージ。
4. **エラー急増（Sentry）**: 発生ビュー/ブラウザを特定 → 再現 → 修正 or ロールバック。
